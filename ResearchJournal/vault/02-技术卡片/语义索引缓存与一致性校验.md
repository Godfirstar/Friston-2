# 语义索引缓存与一致性校验


---

### 2026-10-19 · [[01-版本记录/2026-10-19_174844-f1bf76d793]]

缓存像把常用资料留在桌上：连续查询可以复用编码器与索引矩阵，每个问题仍需计算查询嵌入。

本轮 `friston2/knowledge/semantic_index.py` 为 `_encoder()` 添加容量为 1 的缓存，为 `_read_index()` 添加容量为 2 的缓存。索引键为：

$$K=(P,t_{\mathrm{ns}},N)$$

$K$ 表示缓存键，$P$ 表示绝对路径，$t_{\mathrm{ns}}$ 表示纳秒修改时间，$N$ 表示文件字节数。两个缓存条目可以是同一文件的不同版本，缓存仅在当前进程中复用。

`search()` 仍调用数据库签名函数，并检查索引内的数据库签名和模型标识。需要区分：这些校验保留，不代表每次重新读取索引内容；内容改变但缓存键不变时，仍可能复用旧数组。

工程取舍是减少重复加载机会，同时增加资源驻留时间。本轮没有延迟或内存测量，不能声称已经加速或节省内存。

### 2026-10-21 · [[01-版本记录/2026-10-21_094307-94b15d5d09]]

本次增量补充：`SemanticIntentRouter.prepare()` 用模型名、样例文件原始字节的 SHA256 和 `v2` 组成缓存版本；读取时还核对向量行数和标签数组。原始字节参与摘要，意味着只调整 JSON 排版也可能触发重建。

新索引通过同目录临时文件写入后再替换目标文件，减少目标文件只写了一部分时被读取的风险；这不代替内容校验。本段未见缓存向量维度、有限值和单位长度检查。

异常范围也是缓存设计的一部分：创建缓存目录位于写入异常捕获范围之外，失败会由调用方禁用语义路由。不能仅凭“内存索引仍可用”的注释认定所有持久化失败都能降级。

### 2026-10-21 · [[01-版本记录/2026-10-21_213737-9fe6d9b904]]

本次增补依据：`friston2/skills/npc.py` 的 `_source_stamp`、`_remember` 和观点追问复用分支。这里缓存的是话题中保存的证据，不能据此声称语义索引缓存实现被修改。

具体例子：刚用一件行为支持人物评价，紧接着被问“为什么这么觉得”，新版允许在话题、追问短语、保存来源和来源标记均满足条件时复用资料。

新增的学习点是：**复用需要同时检查用途是否匹配，以及来源是否可能变化。** 本次来源标记由数据库、WAL 文件和角色 JSON 的修改时间与大小组成；它不是内容哈希，也不是原子快照。标记相同只能满足这段代码的复用条件，不能严格证明所有依赖或内容都未变化。

追踪记录将复用来源与检索来源分开，有助于解释回答如何取得证据。复用命中率、陈旧资料风险和实际节省耗时均未测量。
