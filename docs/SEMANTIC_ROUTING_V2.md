# Friston-3 · Agentic RAG v2 · 语义证据需求路由

## 为什么不继续追加关键词

`Agent` 的轻量路由只决定要不要额外询问**设备技能** Planner，并不会自动跳过 NPC 内的知识检索。`NpcTalkSkill` 里的 `conversation_act()` 是表达风格线索，不是判定事实证据需求的无限白名单。

「吃了吗」那轮发生的是 Qwen 路由请求在三秒后超时，旧版把所有路由错误统一回退为 RETRIEVE，才把毫无关系的吃饭故事送给原文选择器。分类问题与超时策略是两个需要分开解决的问题。

## 新的结构

1. **可信执行边界先行**：记忆命令、真实设备执行记录继续走原通路；角色自身身份和能力问答仍要求可靠设定来源；尚未接入的实际财务数据不允许用游戏剧情代替。
2. **语义证据需求分类器**（`friston3/npc/intent_router.py`）：对独立的标注对话示例做 FastEmbed Embedding，采用类别 Top-3 近邻得分、Top-5 类别一致度和类别间隔。分类标签是 CHAT、KNOWLEDGE、LIVE、FOLLOWUP；它们不等同于模型路由的输出枚举。该指标不是经过校准的后验概率，需结合人工误判日志调阈值。
3. **高置信快捷路径**：CHAT 使用 `NPC_CHAT_PROMPT` 生成一次自然回复而非路由 JSON；KNOWLEDGE 直接进入现有知识检索；LIVE 无实时来源时诚实说明；FOLLOWUP 或 UNCERTAIN 进入原 Qwen 上下文路由。
4. **上下文路由**：仅在需要时由 Qwen 根据请求、历史和话题选择 CHAT / RETRIEVE / LIVE / CLARIFY。CHAT 可附自然短答，其余路由的回复字段为空；路由输入没有原作证据，不能靠模型记忆编造人物事实。路由返回枚举中没有 REUSE。
5. **有界事实生成与复核**：RETRIEVE 提供带主体与出处的证据，Qwen 据此生成 Friston-3（自称 Friston）的自然台词，以 E 编号记录实际依据但不念给用户。同一轮最多生成4稿，由同一 `qwen3.5:9b` 通过 `evidence_review` 核对完整草稿与实际送入的材料、修正漏选或错选的来源，并选择接受、重写或针对具体缺口补查。相邻两稿的文本、提议来源编号、完整来源记录及问题与历史上下文均相同，且前次复核为 `accept` 时，可复用该次内容复核；来源归属和本地边界仍重新检查，不能据此跳过原有错误。补查最多2次，仍使用现有检索器；没有新增证据、查询重复或无效、检索失败或剩余预算不足时停止补查，在剩余生成预算允许时回答有依据的部分并说明具体未知。允许综合相关资料，不要求存在标准定义句，也不把个案扩成必然机制；普通概念、关系问题默认一至两句先答核心，保留必要条件与否定，不硬截句或改变 token 上限。同模型复核不是独立事实认证。来源片段不直接充当普通问答台词；只有明确要求原文时使用专门的引用路径。
6. **失败与证据隔离**：路由超时或解析失败默认使用内部失败状态 REFUSE，不把错误解释成检索需求；`FRISTON_AGENTIC_FALLBACK=retrieve` 仅保留为显式兼容选项。生成超时、预算耗尽、异常或最终检查失败返回 `success=False` 的文字诊断，不送 TTS、不写入正常对话历史。补查围绕原问题及具体证据缺口提出查询，不将失败草稿全文作为检索请求；草稿和复核意见都不是事实来源。闲聊检查失败仍只在剩余预算内重写一次。话题中只保留最终采用的事实来源；部分明确观点追问可沿用来源状态未变化的上一轮证据，新的事实请求仍按需检索。用户自述和模型历史台词不是原作证据。
7. **避免无效重写**：本地时序错误带上具体触发片段、触发词和中文修改要求，后续复核通过 `pending_checks` 检查是否落实。相同草稿在相同资料下再次触发相同错误时，下一稿仅接收问题片段及修改要求，不再反复提供整段旧稿；仍无进展则提前停止，记录 `repair_stop_reason`。获得新证据会重置无进展状态。4稿是上限，不是必须执行的次数，也不通过放松本地规则来强行采用答案。

## 数据、性能和可维护性

- `data/knowledge/intent_examples.json`：独立的带标注意图样本。为了覆盖话语功能，包含同义表达、口语、省略、事实提问、实时问题与带闲聊前缀的事实混合问句；它不是 FAQ 命中表。
- `data/runtime/intent_semantic.npz`：轻量索引的自动持久化缓存；根据样本文件与所用 Embedding 模型指纹作废并重建；不是原作知识库索引。
- 使用原有 `BAAI/bge-small-zh-v1.5` FastEmbed `_encoder()`，不常驻新的 LLM。本轮不自动重建 `terra_lore.db`；沿用用户现有角色卡、意图样本、知识库和语义索引，本附件不包含这些 `data/` 文件。首次建立意图缓存可能比后续读取缓存慢。未安装 FastEmbed / 模型不可用时仍可使用 Qwen 路由，但不会伪称分类成功。
- `FRISTON_INTENT_ROUTER=0` 仅关闭意图分类器。`FRISTON_AGENTIC_RAG=0` 关闭新路由和补充检索，保留初次检索；事实回答仍最多2稿，保留同模型复核及严格相同输入下的复用、本地检查和无进展停止，不是撤销全部回答检查。
- 三个 `FRISTON_INTENT_*` 阈值均可在 PowerShell 里配置（详细看 README）。数值来自保守设计起点，**尚未通过人工保留样本校准**；不要将日志里打印的相似度解释成正确概率。
- 路由、回答与证据复核保留同一 `qwen3.5:9b` 模型，没有新增常驻模型或在线 Cross-Encoder；复核及重写会增加实际调用与耗时。路由等待默认3秒，整轮模型请求预算默认60秒；每次将剩余预算传给 `urlopen`。这是网络等待与故障配置，不是严格墙钟截止时间，也不代表已提速。关闭 Agentic 模式不恢复旧4.5秒限制。
- TTS 保留常驻子进程、异步预热和分段音频流程；当前先获得完整 Qwen 文本再送语音，不宣称实现了 token 到语音的流式处理。

## 手动验收清单（不生成或运行自动测试）

进入项目根目录，`conda activate photorobot`，设置 `$env:FRISTON_AGENTIC_RAG="1"` 和 `$env:FRISTON_AGENTIC_FALLBACK="semantic"`，然后 `python main.py`。先观察 `[IntentRouter]` 的启动消息。

- 不同口语问候与关心（包括不在意图样本中的新句式）：目标 `CHAT`、`retrieval_calls=0`，`chat_generation` 通常只调用一次 Qwen。
- 「介绍一下自己」「说说你的历史」：目标检索角色自我档案，而非仅回答「我是 Friston」。
- 明确的人物身份、事件因果、关系问题：目标 `RETRIEVE`，不能只有闲聊回答；事实草稿应有实际 `evidence_review` 或满足严格相同输入条件的复用记录，不能要求每稿新增一次复核调用。
- 概念解释与缺口补查：普通问题默认一至两句先答核心，保留必要限定，不硬截输出；没有标准定义句时可综合有依据的记载，但不能编造机制或扩大范围。若触发补查，核对最多4稿、2次补查；重复查询或没有新增证据后停止补查，在剩余预算允许时保留能回答的部分、限定未知；预算耗尽时明确失败。
- 重写无进展：若触发时序错误，核对触发片段、触发词、中文修改要求及后续复核的 `pending_checks`；同错误重复后应切换只提供问题片段的聚焦重写，再无进展应提前停止。复用内容复核时本地检查仍应执行；新增证据应重置无进展状态。
- 实时资金、现场信息：无真实数据源时明确说不知道，不查游戏背景冒充实时证据。
- 角色事实后「那她后来怎么样」「为什么」：明确指代后按需检索；符合既有观点解释条件时可沿用上一轮实际采用的来源，缺乏先前主体时先澄清。
- 「你好，陈是谁」等混合请求：寒暄不能遮盖事实子请求。
- 每类检查一次「查看证据」：`agentic_rag.semantic` 报告近邻情况，`model_decision` 仅在运行 Qwen 路由时有值；检查 `sent_sources`、`used_source_ids`、`ollama_calls` 与最终 `output_origin`。事实生成还应核对 `answer_attempts` 中每稿的输入、来源、复核结果及 `local_diagnostics`；复用时查看 `review_reused_from_attempt`，无进展时查看 `no_progress` 与 `repair_stop_reason`。同时核对 `retrieval_rounds` 中各次查询与材料，以及 `additional_retrievals`、`semantic_review_performed`。普通事实回答应来自模型；生成失败应标为失败、无播音，不能被原文摘录伪装成成功。`generation_accepted`、同模型复核通过及复用均不等于人工语义全通过。
- 关闭模式：退出后设置 `$env:FRISTON_AGENTIC_RAG="0"` 并重启，确认 `LEGACY` 不调用 `agentic_route`、不补查，但事实回答仍最多2稿并进行 `evidence_review`。
- 确认实际性能：记录 `elapsed_s`、`model_phases`、`retrieval_calls`，在人工标注的多样化问句上估计闲聊误检率、事实漏检率、P95。不能以几条示例就声称已校准。

这是架构修改，不是已经在你的 Windows / GPU / Ollama 环境进行的动态验收。建议先保持严格阈值：遇到语义不确定宁可走上下文模型，也不要贸然将世界观事实分到普通 CHAT。
